
# DECISIONS.md

## Вариант

Номер варианта: 4.

### Часть А

В классе `Order` необходимо ограничить количество
уникальных позиций заказа десятью.

Метод `addProduct()` должен выбрасывать
`IllegalStateException`, если пользователь пытается
добавить одиннадцатый уникальный товар.

При этом объединение товаров с одинаковым ID
разрешено, если итоговое количество не превышает 100.

### Часть Б

Добавить публичный метод
`addPositionCount(Order order)`, возвращающий `int`.

Метод определяет число уникальных позиций
в заказе через `order.getItems().size()`.

## Решение 1

### Формулировка

Проверка ограничения в 10 позиций реализована
в методе `Order.addProduct()`.

Сначала метод проверяет состояние заказа,
корректность товара и количество.

Затем выполняется поиск существующего товара по ID.
Если товар найден, его количество увеличивается.

Если товар новый, проверяется `items.size() >= 10`.
При достижении лимита выбрасывается исключение.

### Альтернатива

Можно было разместить проверку в `OrderService`
или непосредственно в `SelfCheck`.

### Обоснование

Класс `Order` управляет составом заказа и содержит
коллекцию `List<OrderItem>`.

Поэтому именно он должен контролировать ограничение.
Такое решение сохраняет инкапсуляцию и не позволяет
обойти правило через другой способ вызова метода.

## Решение 2

### Формулировка

Метод `addPositionCount(Order order)` добавлен в `Order`.

Он принимает объект заказа, проверяет его на `null`
и возвращает размер списка позиций.

Для получения списка используется `getItems()`,
который возвращает неизменяемую копию.

### Альтернатива

Можно было создать отдельный класс для подсчёта
позиций или хранить количество в отдельном поле.

### Обоснование

Отдельное поле пришлось бы обновлять при каждом
добавлении и удалении товара.

Использование `getItems().size()` исключает
рассинхронизацию значения со списком.

Для небольшого учебного приложения отдельный
сервис подсчёта также не требуется.

## Ответы на контрольные вопросы

### Вопрос 1

Какая проверка защищает программу от наиболее
вероятной ошибки входных данных и где она расположена?

Одной из наиболее важных проверок является
валидация количества товара в классе `OrderItem`.
Метод `setQuantity()` проверяет, что значение
находится в диапазоне от 1 до 100 включительно.
Если пользователь передаст нулевое, отрицательное
или слишком большое количество, программа выбросит
`IllegalArgumentException`.
Дополнительно метод `increase()` проверяет,
что прибавляемое количество положительно.
При увеличении он использует `setQuantity()`,
поэтому ограничение сохраняется и после объединения
одинаковых товаров.
Это предотвращает появление некорректных позиций
и неправильный расчёт стоимости заказа.
Проверка находится в `OrderItem`, потому что именно
этот класс отвечает за количество конкретного товара.

### Вопрос 2

Какой метод содержит ключевое бизнес-правило
и почему оно размещено именно там?

Ключевым методом приложения является
`Order.addProduct()`, который управляет добавлением
товаров в заказ.
В нём реализовано объединение позиций с одинаковыми
идентификаторами, а также запрет изменений
подтверждённого заказа.
Для варианта №4 этот метод дополнен ограничением
на десять уникальных позиций.
Проверка выполняется после поиска товара по ID,
чтобы существующие позиции можно было объединять
даже при заполненном заказе.
Такое расположение бизнес-логики выбрано потому,
что объект `Order` непосредственно владеет списком
`OrderItem` и отвечает за его корректность.
Если перенести правило в `SelfCheck`, оно будет
работать только в тестах и сможет быть обойдено
другим вызывающим кодом.

### Вопрос 3

Как Activity-диаграмма отражает конкретный
участок программного кода?

Activity-диаграмма показывает последовательность
формирования заказа и соответствует логике метода
`Order.addProduct()`.
Сначала выполняется проверка входных данных,
после чего определяется, существует ли уже товар
с указанным идентификатором.
Если товар найден, его количество увеличивается
с помощью метода `increase()`.
Если товар отсутствует, выполняется проверка
количества уникальных позиций.
При наличии свободного места создаётся новый
`OrderItem`, а при достижении десяти позиций
новый товар отклоняется.
Далее алгоритм допускает ввод следующей позиции
или переходит к расчёту общей стоимости.
Таким образом, диаграмма отражает ветвления
и цикл обработки товаров, не повторяя каждую
строку программного кода.

### Вопрос 4

Какое изменение требования должно затронуть
минимальное количество классов и почему?

Примером небольшого изменения требования является
изменение максимального числа уникальных позиций
заказа с десяти на двенадцать.
Для этого достаточно изменить проверку
в методе `Order.addProduct()`.
Остальные классы не зависят непосредственно
от конкретного ограничения.
`Product` по-прежнему отвечает за информацию
о товаре, а `OrderItem` контролирует количество
единиц товара в отдельной позиции.
`OrderService` продолжит создавать объекты заказа
без изменения своей логики.
При этом потребуется обновить тесты,
контрольные данные CSV и описание Activity-диаграммы.
Такое разделение ответственности упрощает
сопровождение программы и уменьшает риск
внесения ошибок в несвязанные компоненты.

## Фрагмент кода для анализа

Исходный метод `getItems()`, возвращающий
непосредственно поле `items`, нарушает инкапсуляцию,
поскольку внешний код получает доступ к изменяемой
внутренней коллекции объекта `Order`.
Например, вызов
`order.getItems().add(new OrderItem(product, 1))`
позволил бы добавить позицию в обход метода
`addProduct()`, а значит, обойти проверку состояния
заказа и ограничение десяти уникальных позиций.
Для устранения проблемы используется выражение
`return List.copyOf(items);`, которое создаёт
неизменяемую копию списка и не позволяет внешнему
коду добавлять или удалять элементы коллекции.
Альтернативой является
`Collections.unmodifiableList(items)`,
однако этот вариант создаёт неизменяемое представление
исходного списка, а не независимую копию.
Выбранное решение соответствует правилу R11
методических указаний и защищает состав заказа
от прямой модификации извне.
